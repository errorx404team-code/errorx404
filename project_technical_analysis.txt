1. PROJECT OVERVIEW
================================================================================

1.1 Project Purpose:
ErrorX404 is an end-to-end, AI-powered legacy code modernization and intelligence
platform engineered to automate the transformation of monolithic, legacy codebases
— specifically MUMPS (Massachusetts General Hospital Utility Multi-Programming
System), the foundational language powering the Veterans Affairs (VA) VistA
Electronic Health Record (EHR) system — into modern, modular, object-oriented
Python (with support for R).

1.2 Problem Being Solved:
Legacy healthcare EHR systems like VistA manage mission-critical clinical workflows
and patient data records across hundreds of hospitals. However:
- MUMPS code suffers from dense, cryptic syntax ($GET, $DATA, ^DPT globals, untyped
  variables, tag-based goto/do jumps).
- MUMPS domain experts are retiring, creating massive institutional risk.
- Manual conversion of millions of lines of code is error-prone, extraordinarily
  expensive, and risks clinical regression.
- Naive LLM code translation often hallucinates business rules, silently drops
  cross-file dependencies, fails to preserve state mutations, and cannot verify
  correctness against legacy runtime behavior.
ErrorX404 solves this by combining static AST/regex analysis, dependency graph
reconstruction (inspired by IBM Mono2Micro), multi-level specification extraction,
context-window-aware LLM code transformation (Google Gemini API), isolated sandboxed
subprocess test execution, automated confidence scoring, plain-English NLP human
understanding, and a VS Code-style IDE in the browser.

1.3 Target Users:
- Software Engineers & Modernization Architects: Analyzing legacy code structure,
  dependency networks, and reviewing generated Python architecture.
- Healthcare IT & Clinical Domain Experts: Reviewing business logic preservation
  and verifying clinical rule fidelity via the plain-English Human Understanding layer.
- QA & Compliance Engineers: Inspecting sandbox test execution results, confidence
  scores, interface contracts, and audit traces before approving production export.

1.4 Overall Application Workflow:
1. Routine Upload: Single files or entire nested directories (.m, .mps, .rou, .cob,
   .sql, .py) are uploaded through the browser IDE or dragged into the file tree.
2. Workspace Isolation: Uploaded batches are tagged with a unique workspace UUID.
3. Spec Extraction (Module 1): MUMPSAdapter parses routines; Gemini extracts
   structured specifications and numbered business rules (RULE-1, RULE-2, etc.).
4. Dependency Graph & Partitioning (Modules 1b & 1c): Static analysis builds per-routine
   and cross-file dependency graphs and computes cohesion/coupling metrics.
5. Conversion Planning: DependencyResolver performs topological sorting (Kahn's algorithm)
   and DFS cycle detection to generate an execution plan (leaf modules first).
6. Code Transformation (Module 2): Gemini generates Python code injecting interface
   contracts, dependency context, and traceability headers (# Modernized from: ...).
7. Sandboxed Verification (Module 3): Independent test cases execute against the
   generated Python code in an isolated subprocess sandbox.
8. Confidence Scoring (Module 4): Algorithmic score (0-100) calculated from test pass
   rates, code complexity, failure severities, and dependency preservation.
9. Human-in-the-Loop Review (Module 5): Developers inspect diffs, test outputs,
   and approve, reject, or rollback conversions.
10. Project Integration Verification & Export: Project-level syntax/import checks
    are executed, and complete modernized code, test suites, and manifests are exported
    as a ZIP archive.

1.5 Main Business and Technical Objectives:
- Guarantee zero-drift preservation of healthcare business logic and data structures.
- Prevent regression through isolated sandbox execution and automated test generation.
- Eliminate dependency breakage across multi-file modularization.
- Demystify legacy code for non-technical stakeholders via plain-English explanations.

5. FEATURES
================================================================================

--------------------------------------------------------------------------------
Feature 1: Multi-File & Folder Batch Upload with Workspace Isolation
--------------------------------------------------------------------------------
- Description: Users can upload single .m files, paste raw code, or upload entire
  hierarchical project folders through drag-and-drop or folder selection.
- How It Works: Files are read in the browser, preserving webkitRelativePath. Backend
  persists relative_path and assigns a common workspace_id UUID.
- Relevant Files: src/components/SidebarFileTree.jsx, backend/app/main.py,
  backend/app/pipeline/file_classifier.py.
- APIs Involved: POST /api/routines/upload, POST /api/routines/upload-files.
- Database: routines table (relative_path, workspace_id, file_action).

--------------------------------------------------------------------------------
Feature 2: Legacy Code Parsing & Business Rule Extraction (Module 1)
--------------------------------------------------------------------------------
- Description: Tokenizes legacy MUMPS routines and synthesizes structured JSON specifications
  along with explicit numbered business rules (e.g. RULE-1, RULE-2).
- How It Works: MUMPSAdapter tokenizes tags, ^globals, and external calls using regex.
  SpecAnalyzer prompts Gemini to extract high-level summaries, functional purposes,
  explicit business rules, and edge cases.
- Relevant Files: backend/app/adapters/mumps_adapter.py, backend/app/pipeline/analyzer.py.
- APIs Involved: POST /api/routines/{id}/analyze.
- Database: specifications table (spec_json, spec_readable_text, business_rules_json).

--------------------------------------------------------------------------------
Feature 3: Dependency Graph Reconstruction & Cross-File Signal Detection (Module 1b)
--------------------------------------------------------------------------------
- Description: Maps all intra-routine and inter-routine dependencies into an interactive graph.
- How It Works: DependencyBuilder and file_classifier extract routine calls, global accesses,
  and import statements. ProjectAnalyzer records cross-file edges.
- Relevant Files: backend/app/pipeline/dependency_builder.py,
  backend/app/pipeline/file_classifier.py, src/components/DependencyGraphPanel.jsx,
  src/components/DepReviewModal.jsx.
- APIs Involved: POST /api/routines/{id}/dependency-graph, GET /api/workspaces/{id}/graph.
- Database: dependency_graph, workspace_dependency_edges tables.

--------------------------------------------------------------------------------
Feature 4: Business Logic Partitioning (Mono2Micro-Inspired, Module 1c)
--------------------------------------------------------------------------------
- Description: Automatically clusters functions into functional domains (Patient Validation,
  Prescription Calculation, State Management) with cohesion and coupling metrics.
- How It Works: BusinessPartitioner groups tags based on healthcare domain keywords and
  calculates cohesion % and coupling % scores.
- Relevant Files: backend/app/pipeline/business_partitioner.py, src/components/BottomPanel.jsx.
- APIs Involved: POST /api/routines/{id}/business-logic-map.
- Database: business_logic_partitions table.

--------------------------------------------------------------------------------
Feature 5: Dependency-Aware Conversion Planning & Cycle Detection
--------------------------------------------------------------------------------
- Description: Computes optimal module conversion order and identifies circular dependencies.
- How It Works: DependencyResolver runs Kahn's topological sort and DFS cycle detection,
  scheduling leaf utility files before entry-point routines.
- Relevant Files: backend/app/pipeline/dependency_resolver.py,
  backend/app/pipeline/project_analyzer.py.
- APIs Involved: GET /api/workspaces/{id}/conversion-plan.
- Database: workspace_conversion_plans table.

--------------------------------------------------------------------------------
Feature 6: Context-Window-Aware Code Transformation (Module 2)
--------------------------------------------------------------------------------
- Description: Generates clean, object-oriented Python (or R) code strictly preserving
  business rules, global structures, and cross-file import interfaces.
- How It Works: CodeConverter compiles a comprehensive prompt containing source code,
  interface contracts, dependency maps, and explicit business rules, prepending a
  traceability header comment.
- Relevant Files: backend/app/pipeline/converter.py, backend/app/main.py.
- APIs Involved: POST /api/routines/{id}/convert.
- Database: conversions table (generated_code, model_used, traceability_header).

--------------------------------------------------------------------------------
Feature 7: Subprocess Sandbox Test Execution & Independent Verification (Module 3)
--------------------------------------------------------------------------------
- Description: Executes generated Python code against AI-generated test cases in an
  isolated subprocess sandbox to verify runtime behavioral equivalence.
- How It Works: SandboxRunner writes temporary Python test harnesses, executes sys.executable
  with a 5-10s timeout, captures stdout/stderr, and compares actual vs expected outputs.
- Relevant Files: backend/app/execution/sandbox_runner.py, backend/app/pipeline/verifier.py.
- APIs Involved: POST /api/conversions/{id}/verify, POST /api/conversions/{id}/run.
- Database: test_cases, verification_results tables.

--------------------------------------------------------------------------------
Feature 8: Algorithmic Confidence & Hallucination Scoring (Module 4)
--------------------------------------------------------------------------------
- Description: Assigns an objective 0-100 confidence score and category (Safe, Needs Review, Failed).
- How It Works: Calculated via:
  score = (pass_rate * 0.6) + (complexity_score * 0.2) + (mismatch_severity_score * 0.2).
  In project mode, penalties are added for broken imports and missing dependencies.
- Relevant Files: backend/app/pipeline/scorer.py.
- APIs Involved: GET /api/conversions/{id}/score.
- Database: confidence_scores table (score, category, reasoning_text).

--------------------------------------------------------------------------------
Feature 9: Plain-English Human Understanding Layer & NLP Q&A
--------------------------------------------------------------------------------
- Description: Explains complex legacy routines and conversion decisions in plain English
  tailored to Simple, Business, and Technical audiences.
- How It Works: HumanExplainer synthesizes structured summaries, clinical impacts, and
  risk assessments, with an interactive conversational chatlet grounded on code evidence.
- Relevant Files: backend/app/pipeline/human_explainer.py,
  src/components/HumanUnderstandingPanel.jsx.
- APIs Involved: GET /api/conversions/{id}/human-explanation,
  POST /api/conversions/{id}/human-explanation/ask.
- Database: human_explanations table.

8. AUTHENTICATION AND SECURITY
================================================================================

8.1 Authentication & Authorization Implementation:
- Login / Signup: Not implemented. The application is an internal IDE and developer
  workstation tool running locally without user authentication tiers.
- Protected Routes & JWT: No authorization guards exist on the REST API endpoints.
- Role-Based Access: Not implemented.

8.2 API Security & CORS:
- CORS Configuration: backend/app/main.py applies CORSMiddleware with allow_origins=["*"],
  allow_credentials=True, allow_methods=["*"], allow_headers=["*"].
- Security Impact: Safe for local development on localhost; for public production deployments,
  allow_origins should be restricted to specific frontend domains.

8.3 Sandboxed Code Execution Security:
- Execution Mechanism: sandbox_runner.py executes generated Python code via subprocess.run()
  using sys.executable in a temporary file directory with a strict timeout (5.0s - 10.0s).
- Isolation: Executes in an independent process space, preventing memory corruption or
  crashes in the main FastAPI server.
- Technical Limitation: The subprocess inherits standard OS user permissions; for untrusted
  multi-tenant cloud execution, containerized virtualization (e.g. gVisor, Docker) is recommended.

8.4 Secret Management:
- Sensitive Configuration: Handled via environment variables (GEMINI_API_KEY).
- File Storage: Stored in project root .env file; ignored by git (.gitignore).
- UI Masking: The UI displays masked previews (e.g., AQ.Ab8RN...zFA) rather than raw keys.

8.5 Confirmed Security Findings:
- Confirmed: API endpoints lack authentication mechanisms (designed as a single-tenant IDE).
- Confirmed: Overly permissive CORS (allow_origins=["*"]) configured in main.py.
- Confirmed: Subprocess runner relies on local OS process execution without OS container jails.

12. ERROR HANDLING
================================================================================

12.1 Backend Error Handling:
- API Routes (backend/app/main.py): HTTP 404 HTTPException raised when routines,
  conversions, or workspaces are not found.
- LLM Provider (backend/app/llm_provider.py): Wraps Gemini HTTP requests in try/except
  blocks across candidate model rotation. When API keys fail or return HTTP 400/403/429,
  the system logs warnings and automatically falls back to deterministic local mock logic.
- Execution Sandbox (backend/app/execution/sandbox_runner.py): Handles subprocess.TimeoutExpired
  exceptions, standard error capture (stderr), and non-zero exit codes.
- JSON Parsing: Pipeline modules wrap JSON decoding in try/except blocks with fallback
  default dictionary/list schemas.

12.2 Frontend Error Handling:
- Network Requests: Wrapped in try/catch blocks with console.error logging and Toast alerts.
- Form Inputs: Validates non-empty file payloads and API key strings.
- Graceful Degradation: Missing conversions or specs render clean empty states with
  informative placeholder messages.

12.3 Confirmed Missing Error Handling / Technical Limitations:
- The single-file convert_code endpoint does not stream progress; long Gemini requests
  may hit browser timeouts if network latency exceeds 25 seconds.
- Subprocess sandbox execution uses standard os.remove() in a finally block to clean
  temp files, which could leave temporary files if the OS process terminates abruptly.

13.1 Frontend Performance:

- State Caching: pipelineCache object in App.jsx stores per-routine pipeline results,
  preventing duplicate API requests when toggling between editor tabs.

- Sandboxed Subprocess: Test harnesses run with lean standard library imports and a 5-10s timeout.

13.3 Performance Considerations & Identified Bottlenecks:
- In-Memory ZIP Generation: export_project_zip constructs ZIP archives in io.BytesIO() memory.
  For very large projects (thousands of files), streaming disk-backed temporary archives is recommended.
- Batch Pipeline Sequential Execution: POST /api/projects/run-pipeline executes routines
  sequentially in topological order; async concurrent processing could accelerate large batches.

Workflow Scenario: User Modernizes a Legacy MUMPS Routine into Verified Python

1. User Opens Browser: Navigates to http://localhost:3000.
2. Startup Landing Screen: src/components/StartupLandingPage.jsx displays ErrorX404 logo;
   user clicks "→ Go to Workspace".
3. Frontend Initialization: src/App.jsx mounts; invokes fetchRoutines() and fetchApiKeyStatus().
4. File Discovery & Upload:
   - User uploads patient_check.m via SidebarFileTree.jsx.
   - Frontend sends POST /api/routines/upload-files.
   - Backend file_classifier.py tags it as MUMPS and assigns file_action: "CONVERT".
   - Database creates row in routines table with a workspace UUID.
5. Workspace Tree Rendering:
   - SidebarFileTree.jsx displays patient_check.m under the active workspace.
   - MonacoEditorTab.jsx loads raw MUMPS source in the Monaco Editor editor pane.
6. Triggering Modernization Pipeline:
   - User selects Python target and clicks "Run Pipeline" in MenuBar.jsx.
7. Step 1 — Spec Extraction:
   - Backend calls analyzer.py (SpecAnalyzer).
   - mumps_adapter.py extracts tags (VERIFY, CALC) and global (^DPT).
   - Gemini LLM returns spec_json and explicit business rules (RULE-1: Validate status in ^DPT).
   - Stored in specifications table.
8. Step 2 — Dependency & Business Mapping:
   - dependency_builder.py maps routine-to-global relations; stored in dependency_graph.
   - business_partitioner.py clusters tags into "Patient Identification" & "Prescription Calculation".
   - Stored in business_logic_partitions table.
9. Step 3 — Context-Aware Conversion:
   - converter.py formats prompt with business rules, globals mapping, and interface contracts.
   - Gemini LLM emits object-oriented Python code implementing VistAModule with verify_patient()
     and calculate_dosage().
   - Stored in conversions table with traceability header.
10. Step 4 — Sandbox Test Execution:
    - verifier.py and sandbox_runner.py construct Python driver harnesses.
    - Python subprocess executes test cases; captures actual output and compares against expected.
    - Stored in verification_results table.
11. Step 5 — Confidence Scoring:
    - scorer.py calculates score (e.g. 95.0% - "Safe") based on 100% pass rate.
    - Stored in confidence_scores table.
12. Step 6 — Explanations & Docs Generation:
    - human_explainer.py generates plain-English explanation at Simple/Business/Technical levels.
    - doc_generator.py generates technical markdown documentation.
13. Step 7 — UI Update & Review:
    - MonacoEditorTab.jsx renders generated Python code side-by-side with original MUMPS source.
    - BottomPanel.jsx displays green verification checkmarks, 95% Confidence badge, and Logic Map.
    - User inspects Diff View, reviews tests, and clicks "Accept Conversion".
14. Step 8 — Project Acceptance & Export:
    - Backend records "approved" in review_decisions table.
    - User clicks "Export Project ZIP"; backend streams ErrorX404-ModernizedProject.zip
      containing modernized Python modules, auto-generated pytest files, and modernization-manifest.json.

18. INTERVIEW / PRESENTATION EXPLANATION
================================================================================

18.1 What did I build?
I built ErrorX404, an AI-powered legacy code modernization platform designed as a
full-stack, browser-based IDE (similar to VS Code) that automatically transforms
legacy MUMPS routines from electronic health record systems (like VA VistA) into
modern, verified Python and R applications.

18.2 Why did I build it?
Legacy healthcare and financial systems run on millions of lines of MUMPS and COBOL
code written decades ago. As original developers retire, maintaining this software
costs billions and introduces severe operational risk. Manual conversion takes years
and risks fatal clinical bugs, while naive AI translation hallucinates business logic
and breaks multi-file dependencies. I built ErrorX404 to provide an automated,
dependency-aware, verified, and human-explainable modernization pathway.

18.3 What technologies did I use?
- Frontend: React 18, Vite 5, Tailwind CSS with custom GitHub dark theme tokens,
  Monaco Editor for side-by-side diff views, Recharts for KPI analytics, and Lucide React.
- Backend: Python, FastAPI, Uvicorn ASGI server, SQLAlchemy 2.0 ORM, and SQLite.
- AI & Execution: Google Gemini LLM API (gemini-2.0-flash / 1.5-flash) with local
  deterministic fallback, custom MUMPS regex AST adapters, and an isolated subprocess
  Python sandbox.

18.4 Why did I choose these technologies?
- FastAPI & Pydantic provide high performance, automatic OpenAPI documentation, and
  strict schema validation.
- Monaco Editor gives developers the familiar VS Code editing and diff comparison experience.
- SQLite with additive migrations enables a zero-dependency, self-contained deployment.
- Google Gemini API delivers strong reasoning for complex code translation and structured
  JSON output formatting.

18.5 How does the system work?
When a legacy file or folder is uploaded, the platform parses the MUMPS routine
structure, builds cross-file dependency graphs, clusters functions into business
logic partitions, and uses Kahn's topological sort to determine conversion order.
It prompts Gemini with deep dependency context and interface contracts to emit
idiomatic Python. The generated code is immediately executed against test cases in an
isolated subprocess sandbox to verify behavioral correctness. An algorithmic confidence
score is calculated, and plain-English summaries are generated for stakeholders.

18.6 What are the major features?
- Multi-file directory batch upload with workspace isolation.
- Static MUMPS routine parsing & explicit business rule extraction.
- Dependency graph generation, cycle detection, and Mono2Micro-inspired logic partitioning.
- Context-window-aware LLM code conversion with traceability headers.
- Isolated subprocess sandbox test execution with fuzzy output verification.
- Objective 0-100 confidence & hallucination scoring.
- Plain-English Human Understanding layer with 3 audience levels.
- Multilingual grounded AI chat assistant.
- Project integration verification and one-click ZIP export with automated test suites.

18.7 What were the technical challenges?
- MUMPS Syntax Complexity: Parsing unstructured MUMPS global references (^DPT),
  implicit parameter passing, and line-tag jump structures without a native compiler.
- Hallucination Prevention: Ensuring the LLM does not invent healthcare logic by
  strictly grounding prompts on extracted specifications and business rules.
- Multi-File Dependency Chains: Preventing broken imports across converted modules by
  computing topological dependency plans and injecting interface contracts.
- Safe Execution: Running dynamically generated Python code safely without crashing
  the backend server by isolating execution in a guarded subprocess runner.

18.8 What are the key outcomes?
- 100% automated extraction and preservation of critical business rules.
- Verified runtime correctness through independent sandbox testing.
- Full auditability with before-and-after diffs, explainability traces, and review logs.
- Immediate exportability of production-ready Python packages with automated pytest suites.
