WHAT IS THIS PROJECT?
--------------------------------------------------------------------------------
ErrorX404 is a full-stack web application that automates the modernization of
legacy MUMPS (Massachusetts General Hospital Utility Multi-Programming System)
code — the programming language used in the VA VistA Electronic Health Record
(EHR) system — into modern Python (or R) code.

The platform is built as a VS Code-style dark IDE in the browser. It runs an
AI-powered pipeline powered by Google Gemini LLM that:
  1. Parses and understands legacy MUMPS routines
  2. Extracts business logic and specifications
  3. Converts the code to Python/R
  4. Verifies the output through test execution in a sandbox
  5. Scores confidence & detects hallucinations
  6. Provides human review (approve/reject/rollback)
  7. Auto-generates documentation and explainability traces
  8. Provides an AI chatbot assistant for Q&A about converted code

--------------------------------------------------------------------------------
THE AI PIPELINE — STEP BY STEP
--------------------------------------------------------------------------------
The pipeline processes one MUMPS routine at a time through these modules:

STEP 1 — CODE UPLOAD
  User uploads .m files (MUMPS source files) via the UI file picker.
  Each file is saved as a "routine" record in the DB.
  Multiple files in one batch share the same workspace_id.
  API: POST /api/routines/upload  or  POST /api/routines/upload-files

STEP 2 — SPEC ANALYSIS (Module 1: Legacy Code Understanding)
  The MUMPS adapter (mumps_adapter.py) tokenizes the raw code:
    - Extracts routine name, tag/function names, parameters
    - Identifies global variable accesses (e.g. ^DPT, ^PSRX)
    - Finds external routine calls
  The SpecAnalyzer then sends this parsed structure + raw code to Gemini LLM
  and asks it to extract:
    - Summary of what the routine does
    - List of functions with purpose
    - Explicit business rules (e.g. "RULE-1: Patient DFN must exist in ^DPT")
    - Globals accessed and edge cases
  Result is stored as spec_json + spec_readable_text + business_rules_json.
  API: POST /api/routines/{id}/analyze

STEP 3 — DEPENDENCY GRAPH (Module 1b)
  DependencyBuilder scans the code for function calls, global reads/writes,
  and external routine references. It builds a node-edge graph.
  Stored in: dependency_graph table
  API: POST /api/routines/{id}/dependency-graph

STEP 4 — BUSINESS LOGIC MAP (Module 1c — Mono2Micro inspired)
  BusinessPartitioner groups related functions into logical "partitions"
  (e.g. "Patient Identification", "Prescription Validation") with
  cohesion % and coupling % metrics.
  Stored in: business_logic_partitions table
  API: POST /api/routines/{id}/business-logic-map

STEP 5 — CODE CONVERSION (Module 2: AI-Powered Code Transformation)
  CodeConverter sends the spec_json + business_rules_json to Gemini with a
  strict instruction to generate clean Python (or R) code where every
  business rule is preserved and annotated with a docstring comment.
  Output: executable Python class/functions with proper error handling.
  Stored in: conversions table (model_used = "gemini-2.0-flash")
  API: POST /api/routines/{id}/convert

STEP 6 — VERIFICATION (Module 3: Independent Verification Layer)
  The generated code is executed in an isolated subprocess sandbox
  (sandbox_runner.py) against auto-generated test cases.
  Test cases are LLM-generated from the MUMPS code (3 per routine).
  Fallback test cases target verify_patient(), calculate_dosage() functions.
  Results: actual vs. expected output comparison with fuzzy matching.
  Stored in: test_cases + verification_results tables
  API: POST /api/conversions/{id}/verify

STEP 7 — CONFIDENCE SCORING (Module 4: Confidence & Hallucination Score)
  ConfidenceScorer computes a 0–100 score using:
    score = (pass_rate × 0.6) + (complexity_score × 0.2) + (mismatch_severity × 0.2)
  Categories:
    ≥ 85%  →  "safe"         (green — auto-approvable)
    50–84% →  "needs_review" (yellow — human review required)
    < 50%  →  "failed"       (red — reject / re-run)
  Stored in: confidence_scores table
  API: GET /api/conversions/{id}/score

STEP 8 — HUMAN REVIEW (Module 5: Human-in-the-Loop)
  Reviewer can approve / reject / request changes / rollback a conversion.
  Rollback resets the conversion decision to "reverted".
  Stored in: review_decisions table
  API: POST /api/conversions/{id}/review
       POST /api/conversions/{id}/rollback

STEP 9 — DOCUMENTATION (Module 6: Auto-Documentation Generator)
  LLM generates Markdown documentation for the converted routine covering:
  - Routine purpose, inputs/outputs, preserved business rules, usage examples.
  API: GET /api/conversions/{id}/docs

STEP 10 — EXPLAINABILITY (Module 10: Explainability Panel)
  LLM generates a step-by-step reasoning trace showing why each conversion
  decision was made and how business rules were preserved.
  API: GET /api/conversions/{id}/explain

PROJECT-LEVEL PIPELINE:
  Multiple routines can be processed in one batch.
  API: POST /api/projects/run-pipeline
  Export as ZIP preserving folder structure:
  API: POST /api/projects/export-zip

--------------------------------------------------------------------------------
AI / LLM INTEGRATION
--------------------------------------------------------------------------------
The LLMProvider (llm_provider.py) wraps Google Gemini API with:
  - Candidate model rotation: tries gemini-flash-latest, gemini-2.0-flash-lite,
    gemini-1.5-flash, gemini-2.0-flash, gemini-2.0-flash-exp in order
  - Configurable via GEMINI_API_KEY in the .env file or via the UI Settings modal
  - API key can be saved from the UI (persisted to .env file)
  - Smart fallback mode when no API key is provided:
    Returns hardcoded realistic Python code and spec JSON so the app remains
    functional for demos without requiring a live API key.
  - Temperature: 0.2 (deterministic/precise output)
  - Max tokens: 4096

HOW TO RUN THE PROJECT
--------------------------------------------------------------------------------
PREREQUISITES:
  - Node.js (for frontend, npm)
  - Python 3.8+ (3.14 recommended, as per start-backend.ps1)
  - A Google Gemini API key (optional — fallback mode works without it)

STEP 1: Set up environment variables
  Copy .env.example to .env and add your Gemini API key:
    GEMINI_API_KEY=your_actual_gemini_api_key_here
    PORT=8000
    DATABASE_URL=sqlite:///./modernization.db

STEP 2: Install backend dependencies
  cd backend
  pip install -r requirements.txt

STEP 3: Start the backend server
  Run: .\start-backend.ps1
  OR manually:  cd backend && python -m uvicorn app.main:app --reload --port 8000
  Backend runs at: http://localhost:8000
  API docs at:    http://localhost:8000/docs  (Swagger UI, auto-generated)

STEP 4: Install frontend dependencies
  npm install

STEP 5: Start the frontend dev server
  Run: .\start-frontend.ps1
  OR manually: npm run dev
  Frontend runs at: http://localhost:3000
  (Vite proxies /api/* requests to http://localhost:8000)

STEP 6: Open the application
  Open a browser at http://localhost:3000

--------------------------------------------------------------------------------
WORKSPACE CONCEPT
--------------------------------------------------------------------------------
When multiple .m files are uploaded at once (e.g. a folder), they share
a common UUID workspace_id. The UI groups routines into "workspaces"
represented as tabs in the file explorer. Each workspace is isolated —
you can work on multiple MUMPS projects simultaneously.

--------------------------------------------------------------------------------
DEMO DATA
--------------------------------------------------------------------------------
On first startup, seed_data.py automatically inserts 3 sample MUMPS routines
into the database so the app is immediately usable without uploading files:
  1. A patient verification routine
  2. A medication dosage calculation routine
  3. An order status update routine
These routines simulate real VistA healthcare EHR logic.

--------------------------------------------------------------------------------
PIPELINE CONFIDENCE SCORING FORMULA
--------------------------------------------------------------------------------
score = (test_pass_rate × 0.6) + (complexity_score × 0.2) + (mismatch_score × 0.2)

complexity_score:
  < 100 lines  →  95.0
  < 300 lines  →  85.0
  ≥ 300 lines  →  70.0

mismatch_severity_score:
  0 failures   →  100.0
  1 failure    →  75.0
  2+ failures  →  40.0

Confidence categories:
  score ≥ 85  →  safe         (auto-approve eligible)
  score 50–84 →  needs_review (human approval required)
  score < 50  →  failed       (re-run or reject)

--------------------------------------------------------------------------------
NOTES & LIMITATIONS
--------------------------------------------------------------------------------
- The sandbox execution is subprocess-based; complex MUMPS patterns not
  covered by the hardcoded fallback spec will still require a live Gemini key.
- The COBOL adapter is a stub and does not yet fully parse COBOL source.
- SQLite is used for simplicity; for production, switch DATABASE_URL to
  PostgreSQL or another production-grade RDBMS.
- The app runs fully in fallback/demo mode without a Gemini API key,
  but live LLM-powered conversion quality requires a valid key.
